## Implemented scope

The canonical `.github/workflows/ci.yml` runs for pull requests targeting
`master`, pushes to `master`, and explicit manual validation. Its stable checks
are `quality`, `tests`, `postgresql`, and `container-security`. Pull request runs
cancel superseded work; trusted `master` publication is not cancelled. Workflow
permissions default to `contents: read`; only the trusted publication job gains
`packages: write`. Actions are pinned to immutable commit SHAs and
`pull_request_target` is forbidden.

Python runs as one 3.13 line, with the container pinned to Python 3.13.15 and an
immutable multi-architecture image digest. `requirements/runtime.lock` and
`requirements/dev.lock` contain exact versions and hashes generated by
`pip-tools==7.6.1`. CI rejects stale locks and installs with `--require-hashes`.
Dependabot covers pip, GitHub Actions, and Docker without auto-merge.

The quality gate runs Ruff, Black, mypy, whitespace, lock, workflow-contract,
pip-audit, and redacted Gitleaks checks. Fixable actionable dependency findings
block; findings with no known fix are reported and require a tracked decision.
The PostgreSQL gate uses PostgreSQL 17, executes all deterministic database
integration tests without the credential-gated Google smoke, proves one
Alembic head, upgrades a fresh database, and validates the adjacent
`0022 -> 0021 -> 0022` cycle.

## Container and supply chain

The Dockerfile is multi-stage. The final image contains only the runtime virtual
environment, `app`, Alembic migration source, and `alembic.ini`; it excludes
tests, docs, repository metadata, local environment files, and backups. It runs
one Uvicorn worker as UID/GID `10001:10001`, uses a Python-only liveness
healthcheck, and receives SIGTERM normally.

`BOTWA_BUILD_SHA` is optional in development/test and mandatory in production.
It must be a 40-character Git SHA. `/version` exposes only application name, API
version, and this safe build identity. The OCI image uses
`org.opencontainers.image.revision`, the tag `sha-<master-merge-sha>`, and the
published digest as canonical artifact identity. No runtime secret is accepted
as a build argument.

Pull requests build and scan locally but never publish a trusted image. After
all four gates pass on a real push to `master`, the validated image tar is handed
to the narrowly privileged publication job and pushed to GHCR. That job records
the digest. No `latest` tag exists. A CycloneDX SBOM is generated as a workflow
artifact. Trivy reports all HIGH/CRITICAL findings and blocks fixable ones.
Cosign and managed signing PKI are deferred; GitHub attestation is optional
future hardening because no deployment trust target is frozen.

## Deployment contract

Staging and production promote the same published digest; source is never
rebuilt for production. They use distinct databases, database users, secrets,
HMAC/encryption keys, metrics tokens, and provider credentials. Staging uses the
production security profile with staging-specific credentials. Production adds
an approved GitHub Environment, reviewer, and serialized deployment lock.

The provider-neutral sequence is: acquire the environment lock; select and
verify the immutable digest; validate configuration, database connectivity, and
the backup gate; run exactly one Alembic migration job from that image; verify
current equals head; roll out web; roll out the Automation Worker; wait for
readiness; execute safe smoke checks; verify private metrics and JSON logs; then
complete promotion. Web and worker startup never run migrations.

The migration identity should use a DDL-capable role while runtime identities
should not have schema DDL. Production database TLS, CA handling, snapshots,
restore testing, and provider commands remain hosting-specific. Application
rollback redeploys the previous known-good digest. Database downgrade is never
automatic; schema compatibility is assessed by an operator and future changes
prefer expand/contract.

## Processes and observability

Web, Automation Worker, Billing Due Transitions, and Contacts Backfill all run
from the same immutable image with different commands. Automation is a separate
long-running process and finishes its current batch after SIGTERM before
stopping between iterations. Billing is a platform-scheduled one-shot job,
approximately once per minute, with no overlap. Contacts Backfill remains
manual and always starts with dry-run.

Docker liveness uses `/health/live`; traffic admission and post-deploy checks
use `/health/ready`. The container smoke proves non-root execution, liveness,
database readiness, build identity, and graceful SIGTERM. Hosting must collect
JSON stdout, scrape bearer-protected `/metrics` only over an internal path, and
route required alerts. PRD-023 does not deploy Prometheus, Grafana, a log agent,
or a notification service.

## External administration and go-live gates

Repository administrators must configure `master` protection/rulesets with PRs
and the four stable required checks, block force pushes/deletion as appropriate,
enable GitHub Secret Scanning and Push Protection, enable Dependabot security
updates, configure `staging`/`production` Environments and reviewers, and decide
GHCR visibility. Workflow code does not claim to mutate these settings.

Hosting, DNS, TLS termination, trusted proxy addresses, allowed hosts, CORS,
secret manager, PostgreSQL provider/TLS/roles, backups, restore tests, managed
observability, alert destination, RPO/RTO, and scheduler remain explicit
external decisions. Stable HTTPS routes are required for Meta and Mercado Pago
webhooks. Google OAuth needs separate staging/production callbacks. Real Meta,
Google Calendar, and Mercado Pago sandbox/commercial smokes remain external
enablement gates and are not generic PR checks.
